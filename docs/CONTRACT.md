# Cove implementation contract

Independent SwiftUI iOS 18+ app. MarkdownUI 2.4.1, its cmark 0.5.0 parser, and HighlighterSwift 3.1.0 are pinned SwiftPM dependencies. UI and state live in ios/Cove; the Python backend lives in server/.

## Swift UI contract (root supplies)

`@MainActor final class CoveStore: ObservableObject` injected as environment object. Properties:
- `@Published var selectedTab: Int = 2` (0 home, 1 pulse, 2 chat, 3 health, 4 settings)
- `@Published var messages: [ChatMessage]`, `conversations: [Conversation]`, `activeConversationID: String`, `draft: String`
- `@Published var serverURL: String`, `accessToken: String` (form binding, never print), `connectionStatus: String`, `isConnected: Bool`, `isBusy: Bool`, `errorMessage: String?`
- `@Published var pulse: PulseSnapshot?`, `usage: UsageSnapshot?`, `health: HealthSnapshot?`, `healthSyncedAt: Date?`, `healthReadAt: Date?`, `isSyncingHealth: Bool`, `healthSharingEnabled: Bool`, `healthSyncStatus: String`
- `@Published var previewMode: Bool` (explicit sample preview only), `appearance: String` (system/light/dark), `notificationsEnabled: Bool`
- `func send()` schedules async send using draft. `func retry(_ message: ChatMessage)` reuses ID. `func connect() async`, `func refresh() async`, `func newConversation() async`, `func selectConversation(_ id: String) async`, `func interrupt() async`, `func syncHealth() async`, `func deleteSharedHealth() async`, `func saveSettings()`, `func enablePreview()`, `func exitPreview()`.
- `func sendAttachment(data: Data, filename: String, mime: String) async` optional UI image picker. Don't implement recording/voice in v1.
- `func sendAttachments(files: [CoveOutgoingFile]) async` persists a multi-file outbox before upload; `CoveOutgoingFile` contains `data`, `filename`, `mime`. `attachmentUploadStatus: String?` reports active file ordinal. Each acknowledged file ID is saved before the message POST, allowing restart recovery without resending the acknowledged files. `attachmentData(_ path: String)` reads endpoint-isolated local/cache data or authenticated server data; preview fixtures never call the server.

Models (all Identifiable where appropriate, Codable):
- ChatMessage: id String; conversationID String; role String (user/assistant); text String; createdAt Date; status String (pending/sending/sent/streaming/complete/failed/interrupted); replyTo String?; attachmentURL String?; error String?; attachments [ChatAttachment]?. role == user identifies own bubble.
- ChatAttachment: id String; filename String; mime String; size Int; url String. Legacy single attachmentURL remains readable.
- Conversation: id String; title String; createdAt Date.
- PulseSnapshot: updatedAt Date; summary String; desires [PulseMetric]; physical [PulseMetric]; senses [PulseMetric]. PulseMetric: id String; label String; value Double (0...1); detail String.
- UsageSnapshot: plan String?; updatedAt Date; windows [UsageWindow]; error String?. UsageWindow: id String; title String; usedPercent Double; resetsAt Date?.
- HealthSnapshot: capturedAt Date; metrics [HealthMetric]. HealthMetric: id String (sleep/steps/heartRate/restingHeartRate/hrv/activeEnergy/exercise); title String; value Double; unit String; sampledAt Date; detail String?.

UI labels in Chinese, names 用户 / 助手, display name Cove. Real empty states are default; preview enabled only user action or launch arg --preview. UI should be warm but Telegram-like compact blue/teal chrome, double solid bubbles, no huge hero or gaudy gradients. Five persistent tabs except keyboard hiding normal platform behavior. Home contains avatars + recent dialogue + honest pulse/health summary. Pulse clearly timestamps data and never animates fake realtime heartbeat. Health explicit sharing consent toggle and read/sync distinction. Settings URL/secret form, connect action, quota windows, appearance and push permission. Deep/dark visual support.

## HTTP API (all JSON camelCase, dates RFC3339 ISO8601)

All except GET /health require Authorization: Bearer COVE_TOKEN. Server default binds 127.0.0.1:8796. HTTPS termination external.
- GET /health -> {ok:true, service:"cove"} readiness is not model connectivity.
- GET /v1/conversations -> {conversations:[Conversation], activeConversationID:String|null}
- POST /v1/conversations {id?:String} -> {conversation:Conversation}; persist idempotently if supplied ID, does not wipe old history.
- GET /v1/messages?conversationID=...&after=0 -> {messages:[ChatMessage], cursor:Int, busy:Bool}. cursor monotonic per database; latest changed messages include streaming revisions. Cursor advancement must not skip other conversations; client tracks per conversation. A poll response may page, so continue until caught up.
- POST /v1/messages {id,conversationID,text,replyTo?,attachmentID?,attachmentIDs?:[String]} -> {message:ChatMessage}; ack only after SQLite commit, dedupe persistent ID; duplicate with mismatching body reject 409. `attachmentIDs` contains at most 10 distinct IDs in display order. `text` may be empty when files exist. If both old/new fields are sent, legacy `attachmentID` must equal the first array entry. A legacy one-file retry and the equivalent one-element array have the same durable identity, including records saved by the older backend.
- POST /v1/interrupt {conversationID} -> {ok:true}
- POST /v1/attachments {filename,mime,dataBase64} -> Attachment `{id,filename,mime,size:Int,url}`; any file type up to 20 MiB per file, with 29 MiB JSON request limit. UTF-8 `text` can replace `dataBase64`; exactly one content field is required. MIME is a safe `type/subtype`, filename is a basename without control characters. Save the returned ID before sending/retrying a message; upload alone does not run a model.
- GET /v1/attachments/{id} -> authenticated exact file bytes; `Content-Type` from validated MIME, `Content-Disposition: attachment` (ASCII fallback plus UTF-8 filename*), `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`. HTML/SVG/scripts remain inert downloadable data on the backend.
- ChatMessage JSON additionally includes optional `attachments:[Attachment]`; first file URL also populates legacy `attachmentURL`. Multiple user attachments and model-created reply files persist with their own metadata and stream revisions. Existing one-file history is normalized from its stored attachment URL when available.
- GET /v1/pulse -> PulseSnapshot (normalize existing local Pulse state file; NO mutations/heartbeat).
- GET /v1/usage -> UsageSnapshot (Codex account/rateLimits/read; unavailable error, never fabricated quota). Only the canonical `rateLimitsByLimitId.codex` account bucket is displayed, with backward-compatible `rateLimits` fallback only when its `limitId` is absent or `codex`. Model-specific buckets such as `codex_bengalfox` / GPT-5.3-Codex-Spark are not the current chat model and are excluded. Match actual `windowDurationMins`, not primary/secondary position: 300 → `{id:"codex-5h",title:"5 小时窗口"}`, 10080 → `{id:"codex-weekly",title:"周额度"}`. Only real returned windows are included, so a Pro account returning only a weekly primary window has no fabricated 5h row. Raw `planType` remains `plan` (including `prolite`); iOS supplies a friendly plan label. A later Plus plan naturally displays both windows if actually returned.
- POST /v1/health {snapshot:HealthSnapshot} -> {ok:true,syncedAt:date}
- GET /v1/health -> {snapshot:HealthSnapshot|null,syncedAt:date|null,readAt:date|null} (UI reading never marks readAt).
- DELETE /v1/health -> {ok:true} delete only uploaded Cove copies.
- POST /v1/devices {token:String} -> {ok:true} persist device token for optional APNs config.

## Runtime / backend

Use self-hosted HTTP + durable chat storage, independent Codex app-server stdio JSON RPC adapter. app-server official docs https://learn.chatgpt.com/docs/app-server . Existing Codex account should remain host-local. New app conversations isolated thread IDs, identity workspace configured. Runtime must not seize other applications active thread. One queue worker for sequential turns in first implementation; map stable conversation+turn IDs, handle stream events, retain failures visibly on restart, no blind duplicate turn retry. Add read-only health tool via Codex dynamic tools if supported, or isolated local MCP; record readAt only successful model tool read. No automatic model wakes. Don't send messages to user independently for testing. Tests use fake runtime; any real runtime E2E requires an explicitly authorized isolated test conversation.

No plain fake server responses except explicitly fake runtime for isolated tests. Access tokens/env and APNs p8 are never committed. Implementation limitations must be documented candidly.

### File tools and model input

All new and resumed Cove threads receive the same thread-scoped stdio MCP server `cove_files` through app-server start/resume configuration overrides; host configuration is not rewritten. Installed app-server schema has `dynamicTools` on start only, so new file tools are not silently added through unsupported resume fields or by switching thread IDs. The existing dynamic `cove_health_read` and its successful-handoff readAt semantics remain unchanged.

`cove_create_file {filename,mime,text? ,dataBase64?}` commits exact generated bytes and attaches metadata directly to the current assistant message in the same SQLite transaction (20 MiB/file, 10 files/reply); exactly one content field is required. `cove_send_file {path,filename?,mime?}` exports an existing ordinary file only from explicit dedicated `COVE_EXPORT_ROOTS`. Empty configuration disables path export. Absolute resolved paths must remain in these roots; hidden files, outside symlinks, hardlinks and special files are rejected. Neither tool executes or renders files.

MCP callbacks use a loopback-only server with an independent random conversation capability, never the phone's global COVE_TOKEN. Each call requires the current active thread/turn's matching actual `mcpToolCall item/started` event and arguments. Finished/cancelled/unrelated turns cannot attach a file; repeated tool-event IDs return the same committed artifact. Runtime subprocess/MCP child environments exclude COVE_TOKEN and APNs variables. This adds file delivery capabilities without increasing Codex sandbox permissions.

JPEG/PNG/WebP/GIF files with matching signatures enter vision input, bounded to 20 MiB total per turn. UTF-8 text, HTML, Markdown, JSON/XML and common source file suffixes enter bounded user attachment context (100,000 bytes per file, 200,000 bytes total). Truncation, invalid text, unsupported binaries and image-budget overflow are explicitly reported to the model. PDF/Office/zip/other binary files are transferred faithfully but their contents are not automatically extracted; model must not claim it read them. Markdown stays intact in message text; full Markdown rendering and inert file preview are client responsibilities.

## Current-conversation console API

The console controls the same Cove conversation/thread and durable message queue. It is an app-server execution console, not tmux/SSH or an independent shell/session. All routes require the existing Bearer token. No sandbox mode or host authentication/configuration changes are exposed.

- `GET /v1/terminal?conversationID=...&after=0` → `{conversationID:String,cursor:Int,events:[TerminalEvent],busy:Bool,connected:Bool,threadID:String|null,turnID:String|null,model:String|null,effort:String|null,pendingApprovals:[TerminalApproval]}`. Events page at 200; track a separate cursor per conversation and request successive pages. `busy` includes queued/running jobs; `connected` means the owned app-server process is running, not a guarantee of model/account connectivity. `model`/`effort` are the next-dispatch selection; a switch during execution does not change that active turn.
- `TerminalEvent`: `{id:Int,kind:String,text:String,createdAt:ISO8601,threadID:String|null,turnID:String|null,itemID:String|null}`. Kinds include `input`, `turn`, `command`, `output`, `fileChange`, `tool`, `message`, `approval`, `error`, `model`, `stop`, `help`. Command start/completion/exit code, bounded actual stdout/stderr, file changes and tool names come from current thread/turn notifications. Private reasoning and arbitrary RPC/tool argument/result payloads are excluded. Known environment secrets, bearer values, token-key values and recognizable API/JWT tokens are redacted before log storage. Each event text is capped at 16,000 characters; stdout is redacted as complete lines, with oversized lines dropped. Live-turn log budget is 1,000,000 characters; console logs are durable and distinct from chat messages. Past turns from before this feature have chat history but no reconstructed execution log.
- `GET /v1/terminal/models` → `{models:[{id:String,model:String,displayName:String,supportedEfforts:[String],defaultEffort:String}],updatedAt:ISO8601}`. Reads paginated actual app-server `model/list` (no synthetic fallback); failure is an error. IDs and supported reasoning efforts are supplied by the configured host's catalog, not a promise that an account can execute every listed model.
- `POST /v1/terminal/input {id:String,conversationID:String,text:String}` → `{ok:true,kind:"message"|"stop"|"model"|"help",message?:ChatMessage,model?:String|null,effort?:String|null,text?:String}`. Ordinary nonempty input (up to 100,000 characters) uses the same `Store.accept`/durable queue as chat, same persistent ID identity and 409 on conflicting retries. It is an instruction to Codex in this conversation, not directly executed shell text. `/stop` interrupts this conversation's current turn and cancels its queued messages; `/model` reports the selected next-turn model; `/model <model> [effort]` validates and selects it; `/help` returns help. Unknown slash controls or malformed controls return 400. Control IDs and their original responses persist separately; repeating a prior `/stop` does not stop a newer turn. Control receipts commit before a stop side effect; an uncertain interrupted control request is not automatically replayed after restart.
- `POST /v1/terminal/model {conversationID:String,model:String,effort:String}` → `{ok:true,model:String,effort:String}`. Validates both against actual `model/list`, persists per conversation, then explicitly supplies `model` and `effort` in the next actual `turn/start`, including resumed old Cove threads. It preserves the original thread and workspace. Initial defaults come from `COVE_MODEL` and `COVE_EFFORT` (high by default).
- `TerminalApproval`: `{id:String,conversationID:String,kind:"command"|"fileChange"|"permissions",command:String|null,cwd:String|null,reason:String|null,details:String|null,createdAt:ISO8601,expiresAt:ISO8601,threadID:String,turnID:String,itemID:String,decisions:[String]}`. `details` is a redacted textual description of the requested permission scope/network/root. The opaque `id` is unique per RPC callback, including multiple callbacks for one item. Only single-operation `accept`/`decline` are exposed; command decisions respect advertised available decisions. No session-wide acceptance or policy amendment is exposed. Permission acceptance returns only the exact requested permissions, scoped to this turn.
- `POST /v1/terminal/approval {conversationID:String,approvalID:String,threadID:String,turnID:String,decision:"accept"|"decline"}` → `{ok:true}`. Requires that exact approval and current active thread/turn/conversation with no cancellation. Stale/cross-thread/cross-conversation/duplicate/expired approvals return 409; unsupported decisions return 400. Success means the actual RPC result was written/flushed to the owned app-server pipe, not that execution succeeded. Pending approvals are declined on stop/timeout and discarded on completion/disconnect/restart; they are never restored/replayed into later turns. Default deadline 120 seconds (`COVE_APPROVAL_TIMEOUT`, bounded 1–600). Closing the phone UI or its poll connection does not itself stop a turn; an unanswered approval expires safely. Unsupported elicitation/user-input/login refresh requests remain denied/unavailable.

Adapter defaults remain read-only sandbox plus on-request approval policy. Host-configured `COVE_SANDBOX` and `COVE_APPROVAL_POLICY` are applied to new/resumed threads, with the approval policy also supplied to each turn. If an operator explicitly chooses `never` approval mode, recognized affirmative MCP/tool consent questions and optional-only form elicitations may be accepted automatically. Keep the default `on-request` policy unless these implications are understood; ordinary questions and unsupported requests do not gain a new flow. No terminal/sticker route changes the sandbox, approval policy, host configuration or other applications sessions. In approval-based mode, the phone's explicit acceptance remains scoped to the requested operation/turn. Runtime failures stop the app-server process owned by Cove, visibly fail the uncertain turn and never replay its user input. File/health tools, health `readAt`, attachment transfer, APNs-after-commit and existing chat dedupe remain unchanged.

Console latest-page option: `GET /v1/terminal?conversationID=...&after=0&tail=1` returns the most recent 200 events, ordered ascending, with the cursor at the latest returned event. Subsequent requests omit tail/use `tail=0` and that cursor to receive all newly appended events without gaps. `tail=1` with nonzero `after`, or a tail value other than 0/1, is rejected 400. Omitting tail preserves the existing full-history paging API. The iOS console requests tail on opening/reopening, then drains full incremental pages immediately rather than waiting one poll interval per page.

Cove iOS console shortcuts adapt other applications's agent controls to app-server: `model` opens the real model picker; `clear` and typed `/clear` ask confirmation, stop the old conversation and create a new conversation while retaining its records and inheriting the selected model/effort; `esc` dismisses an approval viewer first, otherwise submits `/stop` for the current conversation. These are app controls, not PTY key sequences or Telegram-native agent features. Approval-viewer dismissal leaves approval pending until an explicit decision or expiry. Clearing changes the local selected conversation only after server creation/model ACKs; failed creation/settings retains the old context and reports the failure. Logs initially scroll to the final line, follow output/keyboard layout while at the tail, and pause when the user scrolls upwards with an explicit latest-log control.

## Private-chat read receipt and reaction

ChatMessage additionally includes `readAt:ISO8601|null` and `isLiked:Bool`. Missing legacy fields normalize to null/false. User receipt semantics: durable acceptance/queued/claimed work remains unread (`readAt=null`); the adapter marks that exact user message only when actual `turn/started` for the active thread or a successful `turn/start` response binds a valid running job to its turn. The update commits with a message revision, so regular polling receives the transition to double-check state. This means the input was accepted into a Codex turn, not a claim the model understood it. A failure before any start/binding, canceled queue item, restart of unstarted work, or repeated failed-message POST never invents a receipt. A known start followed by reply failure remains read. Binding is idempotent; conflicting/cross-thread/previously-used/stale turns cannot mark another message read, and already read timestamps do not change.

`POST /v1/messages/reaction {conversationID:String,messageID:String,isLiked:Bool}` → `{message:ChatMessage}`. The sole private-chat user's like is an explicitly set boolean, not a toggle or fake count. Any existing user/assistant message may be liked or unliked. Missing message/conversation returns 404; cross-conversation returns 400; non-boolean or missing isLiked returns 400. Changes commit before ACK and produce a normal poll revision; repeating the same value preserves the timestamp/other fields and creates no revision churn. Likes survive streaming/finalization and service restart. Read receipts/reactions do not alter the original message dedupe identity or enqueue another model turn.

Every server-returned `ChatMessage` now includes `revision:Int`, the monotonic SQLite message version. The JSON body and indexed revision column use the same committed version; legacy bodies without the field are returned with the authoritative stored column. New acceptance ACK, duplicate ACK, reaction ACK and polling all carry it. Clients merge only newer versions (equal versions are idempotent), preventing late acceptance/reaction/poll responses from overwriting more recent receipts or canceled likes. Older cached/server messages may lack revision; preserve compatibility and never regress a known nonnull readAt while merging an unversioned old response. The database-global poll cursor remains the last returned revision for that conversation and is separate from individual cached message versions.

## Persistent personal sticker libraries (2026-09-14)

`Sticker`: `{id:String,owner:"user"|"assistant",label:String,createdAt:ISO8601,attachment:ChatAttachment}`. Each person has a separate persistent library, capped at 500 records. Labels are trimmed, nonempty, at most 120 characters and have no control characters. Supported images are signature-matching PNG/JPEG/GIF/WebP within the existing 20 MiB attachment limit. Save and send reuse the original attachment bytes; no server decoding, transcoding or animation flattening occurs. SVG/HTML and mismatched MIME/image signatures cannot be saved as stickers. Existing authenticated attachment-download handling stays unchanged.

- `GET /v1/stickers` → `{stickers:[Sticker]}` returns both libraries, ordered by creation time/id, under existing phone Bearer auth.
- `POST /v1/stickers {attachmentID:String,label:String}` → `{sticker:Sticker}` saves an existing uploaded/history attachment into the **user** library. No owner override is accepted. Same `(owner,attachmentID)` is idempotent and preserves its first label, ID and date. ACK follows SQLite commit. Saving does not wake or enqueue a model turn. Upload first using `/v1/attachments`; retain its ID before saving/retrying.
- `POST /v1/messages` additionally accepts optional `stickerID`. When present, `attachmentIDs` must contain exactly that sticker's `attachment.id`; phone users can send a sticker from either library. Empty text is permitted with the attachment. Returned `ChatMessage` includes optional `stickerID` for sticker presentation. It participates in durable message identity; changing/removing the marker with an already accepted message ID returns 409. Older messages without it preserve their original dedupe identity and decoding.
- `cove_list_stickers {}` lists only the assistant's saved stickers with descriptive labels/metadata.
- `cove_save_sticker {attachmentID,label}` saves into the assistant library only when that image occurs on an actual user message in the current Cove conversation, including previously sent history. Unshared uploads and other conversations' user images are rejected. Current input attachment context includes `attachmentID` so the model can name the file without filesystem access. Saving is a model tool action, not an assertion that every incoming image is automatically saved.
- `cove_send_sticker {stickerID}` appends an image from the assistant's own library to its current reply. A one-sticker reply includes `stickerID`; mixed/multiple attachment replies use ordinary attachment presentation. Max 10 total attachments per reply, shared with file tools. No new turn/external message is initiated.

All three tools use the existing thread-scoped `cove_files` stdio MCP bridge on both new and original resumed threads. Every call requires independent loopback capability auth, current conversation/turn, a matching actual `mcpToolCall item/started` event and exact arguments. State is rechecked through the transaction; stale, cancelled and finished-turn calls cannot mutate or list libraries. Repeated tool event IDs return the exact committed result, with no duplicate attachments or revision churn. The model cannot use the phone's global token, assign arbitrary ownership, read unshared uploads, export arbitrary paths or broaden execution permissions through this feature. Libraries and tool receipts survive restart. Rename/delete/reordering are outside this increment.
